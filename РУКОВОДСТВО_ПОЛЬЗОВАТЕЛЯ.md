## 1. Введение и концепция фреймворка

**moa-cc-switch** решает фундаментальную проблему современных LLM: единичные модели склонны к галлюцинациям, пропуску граничных условий и написанию синтаксически корректного, но логически неверного кода. 

Фреймворк объединяет разнородные нейросетевые модели (от облачных API Anthropic, OpenAI, DeepSeek до локальных CLI-инструментов) в единый самокорректирующийся рой. Система замыкает **цикл OODA** (Observe, Orient, Decide, Act — Наблюдение, Ориентация, Решение, Действие):

```
 ┌──────────────────────────────────────────────────────────────┐
 │                        Цикл OODA (MoA)                       │
 └──────────────────────────────────────────────────────────────┘
       ▲                                                 │
       │  (Ошибка верификации / фидбек)                  ▼
 ┌───────────┐   1. Гипотезы   ┌───────────┐   2. Критика  ┌───────────┐
 │ Proposers ├────────────────►│  Critic   ├──────────────►│Aggregator │
 └───────────┘ (Разные LLM)    └───────────┘               └─────┬─────┘
       ▲                                                         │
       │                                        3. Синтез & Tool │
       └─────────────────────────────────────────────────────────┼──────┘
                                                                 ▼
                                                        ┌─────────────────┐
                                                        │  Action Layer   │
                                                        │ (Shell/Pytest)  │
                                                        └────────┬────────┘
                                                                 │
                                                                 ▼
                                                        ┌─────────────────┐
                                                        │   Verifiers     │
                                                        │  (Command/LLM)  │
                                                        └─────────────────┘
```

### Ключевая инновация: Стратегическая цель (`synergy_goal`)
В большинстве систем агентам передается только локальное описание задачи (`task`). В `moa-engine` введено четкое разделение:
* **`task` (Локальная задача)** — конкретное техническое задание (например: *«Написать LRU-кэш на Python»* или *«Провести аудит сайта»*).
* **`synergy_goal` (Стратегическая цель)** — глобальный бизнес-контекст или критерий успеха (например: *«Код должен выдерживать 10 000 конкурентных запросов без блокировок и утечек памяти»*).

> [!IMPORTANT]
> Стратегическая цель транслируется всем участникам роя и независимому LLM-судье при верификации. Если сгенерированный артефакт формально выполняет задачу, но противоречит `synergy_goal`, рой отвергает решение и запускает следующий цикл самокоррекции.

## 2. Установка и быстрый старт

### Требования
* **ОС**: Windows, macOS или Linux.
* **Python**: версия 3.10 или выше.
* **Установленные CLI-инструменты** (опционально, для использования локальных провайдеров): `claude`, `copilot`, `gemini`, `codex`, `kiro`, `agy`, `cc-switch`.

### Шаг 1: Установка пакета
Склонируйте репозиторий и установите пакет в редактируемом режиме (с зависимостями для разработки):

```bash
git clone https://github.com/NickScherbakov/moa-cc-switch.git
cd moa-cc-switch
pip install -e ".[dev]"
```

### Шаг 2: Настройка окружения (`.env`)
Создайте файл `.env` в корневой директории проекта и укажите доступные API-ключи:

```env
# Облачные API ключи (используются при выборе HTTP провайдеров)
ANTHROPIC_API_KEY="sk-ant-api03-..."
OPENAI_API_KEY="sk-proj-..."
DEEPSEEK_API_KEY="sk-..."

# Эндпоинт по умолчанию для CC Switch
CC_SWITCH_ENDPOINT="https://api.anthropic.com"

# Глобальные параметры таймаутов и повторных попыток
MOA_TIMEOUT=60.0
MOA_MAX_RETRIES=3
MOA_RETRY_BACKOFF=1.5
```

### Шаг 3: Проверка работоспособности
Запустите тестовый набор для проверки корректности установки:

```bash
python -m pytest
```
Если все тесты пройдены успешно (`44 passed`), система готова к работе.

## 3. Архитектура когнитивного роя (Роли агентов)

Когнитивный рой состоит из трех ключевых архитектурных ролей, реализованных в модуле `moa_engine.agents`:

| Роль в рое | Класс | Рекомендуемая температура | Назначение и поведение |
| :--- | :--- | :---: | :--- |
| **Proposer** (Генератор) | `ProposerAgent` | `0.5 — 0.8` | Генерирует первоначальные гипотезы, код или решения. В рой рекомендуется включать 2–4 пропоузера с разными провайдерами (например, Claude + GPT + Gemini) для обеспечения разнообразия мышления. |
| **Critic** (Критик) | `CriticAgent` | `0.2 — 0.4` | Строгий QA-инженер и архитектор безопасности. Анализирует все предложения Proposers, выявляет баги, уязвимости, упущенные требования и логические нестыковки. Не пишет код сам, а составляет лист дефектов. |
| **Aggregator** (Агрегатор) | `AggregatorAgent` | `0.3 — 0.5` | Главный архитектор. Изучает гипотезы и критику, синтезирует итоговое идеальное решение и сохраняет его в целевой файл. Имеет эксклюзивный доступ к **Action Layer** для выполнения команд и тестов. |

## 4. Инструменты и Action Layer

**Action Layer** (`moa_engine.tools`) превращает языковые модели из пассивных генераторов текста в активных инженерных агентов. Через реестр инструментов (`ToolRegistry`) Агрегатор может вызывать структурированные функции прямо в процессе рассуждений.

### Стандартный инструмент: `TerminalExecutionTool`
Агрегатор по умолчанию оснащен инструментом `terminal_execution`, который позволяет:
1. Выполнять любые shell-команды в изолированном асинхронном подпроцессе.
2. Запускать автоматические тесты (например, `pytest tests/test_my_module.py`).
3. Выполнять сетевые запросы (`curl`) или проверочные скрипты.
4. Получать вывод `stdout` и `stderr` в реальном времени.

> [!TIP]
> **Цикл самокоррекции**: Если при генерации кода Агрегатор решает запустить проверочный тест через `terminal_execution` и получает в `stderr` ошибку (например, `AssertionError` или `SyntaxError`), он автоматически анализирует трассировку ошибки и переписывает код в той же итерации роя, не дожидаясь внешнего верификатора!

## 5. Режимы работы CLI (`moa-run`)

Основная точка входа в систему — консольная команда `moa-run` (реализованная в `moa_engine.runner`).

### Основные аргументы командной строки
* `--task <текст>` — описание технического задания.
* `--goal <текст>` — стратегическая цель роя (`synergy_goal`).
* `--out <путь>` — целевой файл для сохранения результата (по умолчанию: `result.py`).
* `--verify <команда>` — shell-команда для детерминированной верификации (например: `pytest tests/`).
* `--preset <путь>` — путь к конфигурационному файлу пресета (`.json`, `.yaml`, `.yml`).
* `--context-url <url1> [url2...]` — список веб-страниц для скрейпинга и добавления в контекст задачи.
* `-i`, `--interactive` — запуск интерактивного режима сбора требований (Discovery Chat).

---

### Сценарий 1: Автономная генерация с проверкой тестами
Запуск создания LRU-кэша с автоматической проверкой модульными тестами:

```bash
moa-run --task "Напиши потокобезопасный LRU-кэш на Python с поддержкой TTL" \
        --goal "Код должен быть оптимальным по времени O(1) и выдерживать высокую конкурентную нагрузку" \
        --out "src/my_lru.py" \
        --verify "pytest tests/test_my_lru.py"
```

---

### Сценарий 2: Интерактивный режим Discovery Chat (`-i`)
Перед тем как писать код или анализировать сложные системы, ТЗ часто бывает размытым. Флаг `-i` включает **Discovery Chat** — интерактивное интервью в терминале:

```bash
moa-run -i --task "Создай систему аналитики для интернет-магазина" --out "analytics.py"
```

**Как это работает:**
1. Рой агентов анализирует вашу идею и задает уточняющие вопросы по архитектуре, стеку, граничным случаям и безопасности.
2. Вы отвечаете в терминале прямо на вопросы агентов.
3. **Rolling Summary (Сжатие контекста)**: Чтобы диалог не превысил лимиты токенов LLM при длительном обсуждении, Агрегатор непрерывно сжимает историю переписки в компактное структурированное ТЗ.
4. Когда вы согласны с итоговым техническим заданием, введите команду:
   ```
   /execute
   ```
   Рой завершит интервью, сохранит итоговое ТЗ и приступит к автономной генерации и верификации.

---

### Сценарий 3: Подключение контекста из веб-страниц (`--context-url`)
Если для решения задачи требуется знание внешней документации или анализ сайта, используйте флаг `--context-url`. Фреймворк асинхронно скачает страницы, удалит визуальный мусор и теги (`<script>`, `<style>`, `<meta>`) через `BeautifulSoup4`, и передаст агентам чистый текст:

```bash
moa-run --task "Проведи SEO и UX аудит главной страницы" \
        --context-url "https://infolimp.ru" "https://nopikreport.store" \
        --out "audit_report.md"
```

## 6. Маршрутизация CC Switch, HTTP и CLI провайдеры

`moa-engine` поддерживает гибридную экосистему провайдеров (`moa_engine.clients`), позволяя комбинировать платные облачные API, бесплатные локальные CLI-инструменты и локальные модели Ollama.

### Поддерживаемые провайдеры в `build_client`

| Провайдер (`provider`) | Тип транспорта | Модель по умолчанию | Описание и особенности |
| :--- | :--- | :--- | :--- |
| `anthropic` | HTTP API (`httpx`) | `claude-3-5-haiku-20241022` | Использования Anthropic Messages API. Требует `ANTHROPIC_API_KEY`. |
| `openai` | HTTP API (`httpx`) | `gpt-4o-mini` | Работа через OpenAI Chat Completions API. Требует `OPENAI_API_KEY`. |
| `deepseek` | HTTP API (`httpx`) | `deepseek-coder` | Работа с API DeepSeek (совместим с форматом OpenAI). |
| `ollama` | HTTP API (Local) | `qwen2.5-coder` | Локальные модели на эндпоинте `http://localhost:11434`. Без ключей. |
| `claude-cli` | Subprocess (CLI) | `haiku` (`default`) | Вызов установленного в системе CLI `claude`. Безопасная передача через `stdin`. |
| `copilot-cli` | Subprocess (CLI) | `default` | Вызов GitHub Copilot CLI (`copilot`). |
| `codex-cli` | Subprocess (CLI) | `default` | Вызов Codex CLI (`codex`). |
| `gemini-cli` | Subprocess (CLI) | `default` | Вызов Google Gemini CLI (`gemini`). |
| `antigravity` / `agy`| Subprocess (CLI) | `default` | Вызов Antigravity CLI (`agy`). |
| `kiro-cli` | Subprocess (CLI) | `default` | Вызов Kiro CLI (`kiro`). |

### Безопасность CLI-клиентов (`BaseCLIClient`)
При использовании CLI-провайдеров (например, `claude-cli` или `agy`), фреймворк **не передает** текст промпта через аргументы командной строки (что могло бы вызвать уязвимости Shell Injection или ошибку превышения длины аргументов `ARG_MAX` в ОС). 
Вместо этого промпт безопасно стримится напрямую в стандартный ввод (`stdin`) подпроцесса с параметром `shell=False`.

### Умный роутинг: `CCSwitchClient`
Если указанный провайдер не зарегистрирован напрямую или если вы используете обертку CC Switch, система активирует клиент `CCSwitchClient`:
1. Сначала клиент пытается отправить запрос через облачный HTTP API (используя пул соединений и экспоненциальную задержку при повторах).
2. Если сеть недоступна, ключ отсутствует или API возвращает ошибку, `CCSwitchClient` автоматически и бесшовно переключается на локальную консольную утилиту `cc-switch` в системе.

## 7. Многоуровневая детерминированная верификация

Генерация считается завершенной только тогда, когда артефакт доказал свою работоспособность. Реализованы 3 стратегии верификации (`moa_engine.verifiers`):

### 1. `CommandVerifier` (Жесткая детерминированная проверка)
Запускает shell-команду (тесты `pytest`, линтеры `flake8` / `mypy`, компиляцию скриптов) через `shlex.split`. Артефакт принимается только при коде возврата `returncode == 0`. Любой вывод `stderr` или сбой теста отправляется обратно Агрегатору для новой итерации исправления.

### 2. `LLMVerifier` (Семантическая оценка судьей)
Используется, когда результат нельзя проверить обычными тестами (например, при написании аналитических отчетов, документации или архитектурных RFC). Независимая LLM выступает в роли судьи. Она принимает сгенерированный текст и стратегическую цель `synergy_goal`, возвращая вердикт в формате JSON:
```json
{
  "is_success": true,
  "reason": "Отчет полностью покрывает требования ТЗ и соответствует стратегической цели."
}
```
Если `is_success: false`, аргументация судьи (`reason`) передается рою для доработки.

### 3. `CompositeVerifier` (Цепочка проверок)
Обеспечивает бескомпромиссное качество путем объединения нескольких верификаторов в последовательную цепь. Например:
* **Шаг 1**: Проверка линтером (`CommandVerifier` с `flake8`).
* **Шаг 2**: Проверка юнит-тестами (`CommandVerifier` с `pytest`).
* **Шаг 3**: Семантическое ревью кода на безопасность (`LLMVerifier`).

Цепочка работает по принципу **Short-Circuit** (быстрое прерывание): при падении проверки на любом шаге последующие шаги не выполняются, а рой немедленно получает лог ошибки.

## 9. Наблюдаемость, отчеты и аудит

Каждое действие роя — генерация гипотез Proposers, замечания Critic, синтез и вызов команд Агрегатором, логи `stdout`/`stderr` и вердикты верификатора — фиксируются системой наблюдаемости (`moa_engine.reporter`).

При завершении работы команды (успешном или по достижению лимита `max_iterations`) автоматически создаются 3 артефакта в корневой директории:
1. **`moa_report.html` (Интерактивный HTML-дашборд)** — красивая визуализация процесса с вкладками для каждой итерации, где можно детально изучить, что предлагал каждый агент и почему верификатор отклонял или принимал решение.
2. **`moa_report.md` (Сводка в формате Markdown)** — компактный лог выполнения, идеальный для прикрепления к Pull Request в Git или сохранения в документации проекта.
3. **`moa_trace.json` (Структурированный JSON-трейс)** — машиночитаемый лог со всеми временными метками, токенами и полными текстами сообщений для глубокой аналитики или интеграции в CI/CD пайплайны.

## 10. Решение частых проблем (Troubleshooting & FAQ)

### ❓ Ошибка: `Error executing tool 'terminal_execution': ...` или таймаут команды
* **Причина**: Команда верификации или команда, запущенная Агрегатором, зависла (например, ожидает интерактивного ввода от пользователя или превысила таймаут).
* **Решение**: Убедитесь, что команды в `--verify` или в пресетах запускаются в неинтерактивном режиме (например, используйте флаги `-y` или `--no-input`). Параметр таймаута команд можно увеличить в конфигурации верификатора (`timeout`).

### ❓ Ошибка: `LLMVerifier` постоянно возвращает `is_success: false`
* **Причина**: Чрезмерно строгий промпт оценки в верификаторе, противоречие между `--task` и `--goal`, либо модель-судья возвращает текст вместо JSON.
* **Решение**: Проверьте параметр `evaluation_prompt` в пресете. Убедитесь, что в инструкции судьи четко указано требование возвращать валидный JSON формата `{"is_success": boolean, "reason": string}` без обраткочисел (markdown codeblocks), либо используйте `CommandVerifier` для точных проверок.

### ❓ Сбой переключения CC Switch (HTTP -> CLI)
* **Причина**: При отсутствии интернета или неверном API-ключе система пытается вызвать локальную утилиту `cc-switch`, но она не установлена в PATH.
* **Решение**: Убедитесь, что локальные CLI-инструменты (`claude`, `cc-switch`, `agy` и др.) установлены в вашей операционной системе и доступны из терминала при вызове `which cc-switch` (или `Get-Command cc-switch` в PowerShell).

### ❓ Как ограничить количество итераций самокоррекции, чтобы не тратить токены?
* **Решение**: При использовании пресета укажите параметр `"max_iterations": 3` (или любое желаемое число). Если рой не сможет удовлетворить верификатор за указанное число попыток, выполнение остановится, сохранив лучший текущий результат и сформировав полный отчет об ошибках в `moa_report.html`.
